## 3. NOTIFICATION ARCHITECTURE
Domain event (the Module 31 / 32 order events after their commit; the security events of Modules 21 / 25) → listener → NotificationOrchestrator (registry, policy, template) → one notification row + one delivery row per channel and per device → SendNotificationDeliveryJob on queue "notifications" → provider (push: fcm | fake; e-mail: mail | fake; SMS: fake | off). A business event and a delivery outcome are different things: a delivery failure never changes an order (tested; e2e H3). No outbox exists (CF-414): the notification is written in its own transaction after the event's commit; the dedupe key and the recover sweep are the safety net.

## 4. NOTIFICATION DOMAIN
Tables (one migration, rollback + re-apply checked): customer_devices, notifications, notification_deliveries, notification_delivery_attempts. One logical notification per event, customer and type (unique dedupe key: order id + event sequence + type; security: the event id). Delivery statuses: QUEUED, SENDING, SENT, DELIVERED (never set — no provider gives a trustworthy receipt), FAILED, RETRY_SCHEDULED, CANCELLED, SKIPPED, INVALID_DESTINATION. Attempts are append-only with result, provider code, normalised category, safe error, latency and payload size — never a token, never the raw provider body.

## 5. CUSTOMER DEVICES
One ACTIVE binding per installation and per token (partial unique indexes). The installation id is generated by the app (random; no IMEI, serial or advertising id). The token is encrypted at rest with a SHA-256 hash for lookup and is never returned or logged. The device belongs to the authenticated customer (a customer id in the request is refused). A binding ends on sign-out (LOGOUT), another customer on the same installation (REBOUND + security event DEVICE_REBOUND), the same token on another installation (TOKEN_REASSIGNED), a dead token (INVALID_TOKEN), a customer / admin revoke, or the ten-device limit (REPLACED). A token authorises nothing.

## 6. PROVIDERS
Push: FcmHttpV1PushProvider (implemented; error map UNREGISTERED / SENDER_ID_MISMATCH → invalid destination, INVALID_ARGUMENT → permanent, 429 → rate limited with a 60-second floor, 500 / 503 → transient, 401 / 403 → credential failure; a payload over 4096 bytes is refused before the call; timeout 10 s) and FakePushProvider (deterministic; used locally and in tests; never pretends in a production-like environment). Without credentials the fcm driver reports UNAVAILABLE / PENDING FIREBASE CONFIGURATION.
E-mail: the Laravel mailer with MAIL_MAILER=log locally. REAL EMAIL PROVIDER = PENDING. E-mail also needs a verified address and customers have no e-mail verification yet, so every customer e-mail is SKIPPED today (CF-451).
SMS: a separate contract from the Module 21 OTP sender; fake in tests, off locally. REAL SMS PROVIDER = PENDING (CF-452).

## 11. DELIVERY, RETRIES, DEAD LETTER, INVALID TOKENS
One job per delivery, unique until processing; a lease by conditional UPDATE so only one worker sends; backoff 30 s doubling with jitter, capped at 900 s, five attempts, then FAILED (the dead letter, visible to administrators). 429 waits at least a minute or Retry-After. A credential failure fails the delivery once and pauses the push provider for 300 s (no retry storm). An unregistered token is revoked and never retried; the other devices and the notification stand. notifications:recover (every minute) re-queues stranded SENDING rows, due retries and lost QUEUED rows; notifications:prune (daily) applies retention (90 days, 365 for security, attempts 30). FCM offers no idempotency key, so a crash between the provider's acceptance and our write can produce one duplicate push; the client de-duplicates by notification id.
