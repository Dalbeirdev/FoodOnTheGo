Their causes, as written in m37-regression-notes.txt (obsolete expectations — the product is as designed; the suites are not edited):

- m30_e2e.js (payments) H3 — the step ends with "(mark_paid false, refund NOT_IMPLEMENTED)". The payment detail no longer says refunds are not implemented: it carries the payment's refunds, its refund balance and its disputes, and the action it offers is a refund REQUEST (which moves no money). "mark_paid false" is unchanged, and there is no "mark refunded".
- m30_e2e.js (payments) H6 — the step ends with "the page says … that refunds are not available yet". The page now says that a refund never changes the payment and that refunds are approved and sent in Refund Management. The rest of the step holds (why it needs a person, the provider references, the timeline, no button to mark it paid or to capture).
- m31_e2e_m35.js (orders) C3 — the step reads the refund record from the table order_refunds ("ONE refund record for the whole total (REQUIRED …)"). Module 35 replaced that table by refunds; the read answers the variant's marker "TABLE order_refunds WAS REPLACED BY MODULE 35", so the comparison misses. Everything else the step checks is in its output and unchanged: REJECTED with the reason, the amount unchanged, refund REQUIRED, the reservation RELEASED, the payment still VERIFIED. The record itself is asserted by the Module 35 suite (m35-web-e2e.json, A1: one refund, REQUIRED, the whole total).
- m31_e2e_m35.js (orders) C6 — "REJECTING AGAIN changes nothing … still one refund record" counts the rows of order_refunds; same cause as C3. The Module 35 backend test "the same refund-required condition reported twice makes one refund" and m35 A1 cover it on the new table.
- m31_e2e_m35.js (orders) E3 — the step expects "the refund record (REQUIRED, processing NOT_IMPLEMENTED) … actions … refund NOT_IMPLEMENTED". The admin order detail now lists the order's refunds with their real states and says refund: true for a paid order that is over (a refund can be asked for). The step's own output shows it: {"cancel":false,"refund":true,"mark_picked_up":"NOT_PROVIDED","mark_refunded":"NOT_PROVIDED"}.
- m31_e2e_m35.js (orders) F2 — "A CUSTOMER cannot cancel … an order (404 / 401)" expected 404 because no customer cancel route existed. The route exists now (POST /customer/orders/{order}/cancel): the suite's request has no reason and is answered 422; with a reason it is answered 409 order_cancellation_not_allowed, because customer cancellation is DISABLED pending policy approval (m35-web-e2e.json, E1). The customer still cannot cancel. The other two parts of the step are unchanged (401, 422).
- m32_e2e_m35.js (realtime) G6 — the step expects "/admin/system/orders … refund_processing and notification_delivery NOT_IMPLEMENTED". Refund processing is implemented (Module 35) and the flag says so. The same answer still carried notification_delivery NOT_IMPLEMENTED when this suite ran — a stale flag since Module 33; it was corrected to IMPLEMENTED after the regression (the full backend suite was run again afterwards).
