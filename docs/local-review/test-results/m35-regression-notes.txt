- m31_e2e_m35.js (orders) C3 — the step reads the refund record from the table order_refunds ("ONE refund record for the whole total (REQUIRED …)"). - m31_e2e_m35.js (orders) C6 — "REJECTING AGAIN changes nothing … still one refund record" counts the rows of order_refunds; same cause as C3. The Module 35 backend test "the same refund-required condition reported twice makes one refund" and m35 A1 cover it on the new table.
- m31_e2e_m35.js (orders) E3 — the step expects "the refund record (REQUIRED, processing NOT_IMPLEMENTED) … actions … refund NOT_IMPLEMENTED". - m31_e2e_m35.js (orders) F2 — "A CUSTOMER cannot cancel … an order (404 / 401)" expected 404 because no customer cancel route existed. ## The four variants (m31_e2e_m35.js, m32_e2e_m35.js, m33_e2e_m35.js, m34_e2e_m35.js)

Module 35 replaced the Module 31 table order_refunds by refunds (with refund_attempts, refund_events, payment_refund_balances and payment_disputes). Each of the four order-creating suites deletes from order_refunds in the clean-up it runs BEFORE its first step, so unchanged it stops there with a database error and reports nothing. A variant is a copy of its suite with exactly two differences, both outside the steps:
1. the clean-up statement removes the refund records of the run's orders instead (their attempts and events, the refunds, the payment's refund balance and disputes) — without it the suites could not remove the orders and payments they create;
2. the read helper answers the marker text "TABLE order_refunds WAS REPLACED BY MODULE 35" when a step reads the removed table (two steps of the Module 31 suite do — C3 and C6 above), so that such a step is a recorded miss and not the end of the suite.
The originals (m31_e2e.js … m34_e2e.js) are untouched. How the variants are made is in the session's regress_build.py. The earlier Android preview suites (m31_flutter.js … m34_flutter.js) have the same clean-up statement; they were not run again (see below).

## Procedure
